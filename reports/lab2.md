   其中参数的定义是[63:54]是保留位，[53:10]是物理页号，[7:0]是标志位，标志位的作用如下：

   - 当 V(Valid) 位为 1 时，页表项才是合法的；
   - R/W/X 分别控制索引到这个页表项的对应虚拟页面是否允许读/写/取指；
   - U 控制索引到这个页表项的对应虚拟页面是否在 CPU 处于 U 特权级的情况下是否被允许访问；
   - G 我们不理会；
   - A(Accessed) 记录自从页表项上的这一位被清零之后，页表项的对应虚拟页面是否被访问过；
   - D(Dirty) 则记录自从页表项上的这一位被清零之后，页表项的对应虚拟页表是否被修改过。

2. - 缺页

     缺页指的是进程访问页面时页面不在页表中或在页表中无效的现象，此时 MMU 将会返回一个中断， 告知 os 进程内存访问出了问题。os 选择填补页表并重新执行异常指令或者杀死进程。请问哪些异常可能是缺页导致的？

     - **访存异常（Load/Store Page Fault）**：当进程尝试读取（Load）或写入（Store）一个无效或未映射的页面时触发。
     - **取指异常（Instruction Page Fault）**：当进程尝试执行的指令所在的页面未加载或无效时触发。
     - **权限异常（Access Violation）**：如果页面存在但访问权限不匹配（例如，尝试写入只读页面），也可能表现为缺页异常。

     发生缺页时，描述相关重要寄存器的值，上次实验描述过的可以简略。

     - **scause**：记录异常原因。例如：
       - 取指缺页：`0x0C`（Instruction Page Fault）。
       - 读缺页：`0x0D`（Load Page Fault）。
       - 写缺页：`0x0F`（Store/AMO Page Fault）。
     - **stval**：保存引起异常的虚拟地址（即访问的页面地址）。
     - **sepc**：记录触发异常的指令地址，以便异常处理后重新执行。
     - **satp**：页表寄存器，指向当前进程的页表基地址（简略，之前实验已述）。
     - **sstatus**：状态寄存器，记录特权级别和中断状态（简略）。

     缺页有两个常见的原因，其一是 Lazy 策略，也就是直到内存页面被访问才实际进行页表操作。 比如，一个程序被执行时，进程的代码段理论上需要从磁盘加载到内存。但是 os 并不会马上这样做， 而是会保存 .text 段在磁盘的位置信息，在这些代码第一次被执行时才完成从磁盘的加载操作。这样做有哪些好处？

     1. **节省内存**：只有实际使用的页面才占用物理内存。例如，程序申请大量内存但只使用部分时，避免浪费。
     2. **减少 I/O 开销**：代码段或数据段（如 `.text`）仅在首次访问时从磁盘加载，减少不必要的磁盘操作。
     3. **加速进程启动**：无需在进程初始化时加载全部页面，提升启动速度。
     4. **优化资源利用**：物理内存可分配给活跃进程，提高系统整体效率。

     其实，我们的 mmap 也可以采取 Lazy 策略，比如：一个用户进程先后申请了 10G 的内存空间， 然后用了其中 1M 就直接退出了。按照现在的做法，我们显然亏大了，进行了很多没有意义的页表操作。处理 10G 连续的内存页面，对应的 SV39 页表大致占用多少内存 (估算数量级即可)？请简单思考如何才能实现 Lazy 策略，缺页时又如何处理？描述合理即可，不需要考虑实现。

     1. **内存申请时**：在 `mmap` 或 `sbrk` 时，仅记录虚拟地址范围（如 `MemorySet` 中的 `areas`），不分配物理页面或修改页表。
     2. **标记无效**：为申请的虚拟地址范围设置页表项（PTE）的有效位（Valid bit）为 0，或根本不创建 PTE。
     3. **保存元数据**：记录页面来源（如磁盘上的 `.text` 段位置或匿名内存标记）。
     4. **捕获异常**：MMU 检测到无效 PTE 或缺失页面，触发缺页中断（scause = 0x0C/0x0D/0x0F）。
     5. **检查合法性**：OS 读取 `stval`，验证虚拟地址是否在进程的合法范围（如 `MemorySet.areas`）
     6. **分配页面**：如果是代码段（如 `.text`），从磁盘加载到新分配的物理页面，如果是匿名内存，分配零初始化的物理页面

     缺页的另一个常见原因是 swap 策略，也就是内存页面可能被换到磁盘上了，导致对应页面失效。此时页面失效如何表现在页表项(PTE)上？

     - **Valid bit = 0**：PTE 的有效位被清零，表示页面不在物理内存中。
     - **元数据保留**：PTE 或辅助数据结构可能记录页面在磁盘上的位置（如交换分区的偏移量）。
     - **权限保留**：PTE 仍可能保留原权限信息（读/写/执行），但因 Valid bit = 0，MMU 不会直接使用。
     - **特殊标志**（视系统而定）：某些 OS 用 PTE 的保留位标记页面被换出，而不是完全清空 PTE。

3. 双页表与单页表

   为了防范侧信道攻击，我们的 os 使用了双页表。但是传统的设计一直是单页表的，也就是说， 用户线程和对应的内核线程共用同一张页表，只不过内核对应的地址只允许在内核态访问。 (备注：这里的单/双的说法仅为自创的通俗说法，并无这个名词概念，详情见 [KPTI](https://en.wikipedia.org/wiki/Kernel_page-table_isolation) )

   - 在单页表情况下，如何更换页表？

     1. 保存当前进程的上下文（包括 `satp`）。
     2. 加载新进程的页表地址到 `satp`。
     3. 执行 TLB 刷新（如 `sfence.vma`），确保 MMU 使用新页表。

   - 单页表情况下，如何控制用户态无法访问内核页面？（tips:看看上一题最后一问）

     - **特权级别保护**：
       - 使用页表项（PTE）的权限位控制访问。例如，在 RISC-V SV39 中：
         - 设置 PTE 的 **U-bit（User bit）** 为 0，表示页面仅允许内核态（Supervisor 模式）访问。
         - 用户态（U-mode）访问时，若 U-bit = 0，MMU 触发权限异常（Load/Store Page Fault）。
       - **实现**：内核页面（如内核代码、数据、堆栈）的 PTE 配置为 U-bit = 0，用户页面配置为 U-bit = 1。
     - **模式检查**：
       - MMU 根据当前特权级别（由 `sstatus` 的 SPP 位指示）检查访问权限。
       - 用户态访问内核页面时，硬件检测到 U-bit 不匹配，直接触发异常。
     - **全局映射**：
       - 内核页面通常映射在高地址（如 SV39 的高半地址空间），对所有进程共享。
       - 这些页面在页表中始终存在，但用户态无法访问（因 U-bit = 0）。
     - **与缺页的关系**：
       - 如果用户态尝试访问内核页面，MMU 检测到 PTE 的 U-bit = 0 或页面无效（Valid bit = 0），触发缺页异常。
       - 操作系统检查 `scause` 和 `stval`，识别为非法访问，直接终止用户进程（或返回错误）。

   - 单页表有何优势？（回答合理即可）

     1. **性能开销低**：
        - 进入内核态（如系统调用、中断）无需更换页表，减少 TLB 刷新（`sfence.vma`）和页表切换的开销。
        - 内核和用户共享页表，上下文切换仅需更新一次 `satp`，无需额外维护两套页表。
     2. **内存占用少**：
        - 单页表避免为内核态单独维护一份页表，节省页表内存（尤其在多进程系统中）。
        - 内核页面全局映射，减少冗余 PTE 存储。
     3. **实现简单**：
        - 页表管理逻辑统一，内核和用户地址空间在同一页表中配置，简化操作系统代码。
        - 无需处理用户态和内核态页表同步问题（如 KPTI 需确保映射一致性）。
     4. **TLB 命中率高**：
        - 由于页表不切换，TLB 条目可长期缓存内核和用户映射，减少 TLB 未命中带来的性能损失。
